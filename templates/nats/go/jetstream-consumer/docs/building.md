# Building this template

```bash
make build     # -> jetstream-consumer.wasm
make verify    # assert the export and the async ABI are really there
```

That is the whole build. This template uses **componentize-go's own generated
bindings** directly, so it needs no SDK and no vendored WASI deps — its world
imports only `wasmcloud:nats@0.1.0`.

## Why `-w` is passed explicitly

componentize-go discovers `componentize-go.toml` files from your module *and
its dependencies*, and merges the worlds they name. That is convenient until a
dependency names a world you did not want: the wasmCloud Go SDK's default
world (`wasmcloud:component-go/wasip2@0.2.0`) mandates a
`wasi:http/incoming-handler` export, and merging it fails a NATS component with

```
failed to find export of interface `wasi:http/incoming-handler@0.2.8` function `handle`
```

Passing `-w` pins the build to this template's world and avoids the surprise.

## If you switch to the wasmCloud Go SDK

`go.wasmcloud.dev/component` gives you a friendlier surface — `nats.Message`
with plain `string`/`[]Header` fields instead of `Option[...]`, `error` returns
instead of `Result[Unit, string]`, and typed errors. It costs about 1.8% in
component size and was not measurably slower.

Three things to know before you do:

1. **The handler packages' doc comments name `@0.2.0` interfaces that do not
   exist.** The code is wired to `@0.1.0`, and so is the SDK's own
   `capabilities.wit`. Follow the doc and your world will not resolve.
2. **`doc.go`'s prescribed world mandates an HTTP export**, per the error
   above. Declare your own world with `include wasi:cli/imports@0.2.8` instead
   — that is what the SDK's own NATS example does.
3. **Passing `-w` then drops the WIT paths componentize-go discovered**, so the
   `wasi:cli` deps have to be vendored into `wit/deps/` by hand. The module
   cache is read-only, so the copy needs `chmod -R u+w`.

## Verifying

A Go component that builds but exports nothing is a real failure mode: the
standalone `wit-bindgen-go` generator silently drops every `async func` and
exits 0, producing a component with no handler at all. `make verify` and the CI
workflow both check for it.

## Toolchain facts, verified at the pinned commit

The templates were built with componentize-go `main` at
`20f3b0c2a4127a3efd0c4a00580dc0b409a2f91c` (`go install …@20f3b0c2…`;
`go version -m $(go env GOPATH)/bin/componentize-go` shows module version
`v0.4.2-0.20260827144128-20f3b0c2a412`). Four things about it that are easy to
trip over:

1. **`go.sum` must exist before componentize-go runs.** Both `bindings` and
   `build` start with `go list`, which fails on a checkout without a go.sum
   entry for `go.bytecodealliance.org/pkg`:
   `missing go.sum entry for go.mod file; to add it: go mod download go.bytecodealliance.org/pkg`.
   The templates commit `go.sum`, and `make bindings` runs that
   `go mod download` first anyway (a no-op when the sum is present).
   `wash build` and Cosmonic Desktop's project mode run the bare
   `componentize-go … build` from `.wash/config.yaml` — no Makefile — so they
   rely on the committed `go.sum`.
2. **The generated header says `wit-bindgen` 0.59.0**, not 0.61.1:
   `head -1 wasmcloud_nats_types/wit_bindings.go` →
   ``// Generated by `wit-bindgen` 0.59.0. DO NOT EDIT!``. Confirm the
   generator from that header, never from `componentize-go --version`
   (which says `0.4.1` for every recent commit).
3. **`componentize-go bindings` rewrites the `go.bytecodealliance.org/pkg`
   require in `go.mod`** to the version its generator was built against —
   `v0.2.2` at this commit (it *downgraded* a `v0.2.3` require). `go.mod` ships
   at `v0.2.2` so the rewrite is a no-op. If a different componentize-go
   rewrites it again, commit what it writes together with the regenerated
   `go.sum` (`go mod tidy` follows in the Makefile) rather than editing it
   back: the generated bindings and the runtime package must agree.
4. **The patched Go lands in the OS cache directory**, not always `~/.cache`:
   `~/Library/Caches/componentize-go/v2/go-darwin-arm64-bootstrap` on macOS,
   `~/.cache/componentize-go/v2/…` on Linux. Deleting it forces a re-download.

Two environment notes: put `$(go env GOPATH)/bin` *ahead* of anything else
that provides a `componentize-go` on PATH (a machine that once
`cargo install`ed one has an unrelated 0.3.x in `~/.cargo/bin`), and keep
`GOTOOLCHAIN=local GOFLAGS=-mod=mod GOROOT_BOOTSTRAP_GO=$(go env GOROOT)` set as
the top-level SKILL.md describes.
